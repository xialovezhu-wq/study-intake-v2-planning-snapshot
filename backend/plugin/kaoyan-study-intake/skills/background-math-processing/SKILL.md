# Background Math Processing

Read `../../references/shared-processing-contract.md` completely before processing.

Skill version `4.0.0`.

## Active Multi-Agent V2 route

When `processing_binding_v3` is present, this Skill governs exactly one Luna reader branch. Terra owns read-plan creation, branch selection, fan-in, candidate integration and fresh-context review. This Luna session owns one `branch_id`, one independent read session and one independent subject MCP launcher; it cannot delegate. Later references to a single task-wide Analysis/Critical Review pair describe legacy replay compatibility and are inactive under the V2 binding.

## Input gate

The capture must contain stable identity or a content/source fingerprint, a verbatim `learning_record` task artifact, a distinct `dialogue` task artifact containing the complete dialogue, and bound source artifacts. The learning record and dialogue are distinct immutable artifacts; `capture_facts` may bind only each artifact ID, SHA-256, and content route, never substitute a summary or embedded body. Missing either the learning record or dialogue fails before any model call. A formal-problem capture requires a question image and at least one complete solution evidence form: a solution image or a UTF-8 non-empty `solution_text` copied from a canonical source. A `solution_text` copy is eligible only when the Host verified its absolute canonical source path and SHA-256 before freezing it; the model receives the copied text and source hash, never the local source path. Missing both solution forms fails before any model call. A user-work image is optional when the verbatim reasoning evidence is complete or the user explicitly reports independent success without supplying steps.

Preserve user wording verbatim. Separate independent work, first break, later breaks, hints, self-correction, post-explanation understanding, and unresolved uncertainty. Treat unobserved reasoning as `unknown`; never reconstruct it from the correct result, the formal solution, or missing step-by-step dialogue. Missing evidence produces `needs_review`; never invent it.

## Legacy two-pass compatibility route

The Host dynamically starts `study-read-mcp-math --stdio --read-session-manifest <absolute-v4-json>` as server `kaoyan_math_read`. The exact allowed tool surface is `get_task_context`, `read_task_artifact`, `list_records`, `get_records`, `search_records`, and `query_relations`. Do not use an ordinary bundle, a legacy `math_investigate_library` tool, another subject namespace, terminal, shell, arbitrary path, SQL, plugin, web, or writer tool.

The bootstrap contains only this Skill binding, capture ID, read-session binding, release and Schema hashes, and output instructions. It contains no task prose, image bytes, semantic summary, snapshot, top-k list, local neighbor list, or relation candidates. At the start of Analysis, call `get_task_context`, then read every returned artifact ID with `read_task_artifact`, following every text-artifact cursor until complete. Read the question image and every present solution-evidence artifact: solution images arrive as MCP ImageContent, while `solution_text` arrives as paginated private text with its frozen source hash and a redacted source-path marker. Then use at least one of the four library tools and whichever additional library tools are necessary to establish identity, knowledge, and relation claims.

Select the minimum useful collections yourself from `catalog`, `formal_cards`, `relationships`, `activity`, and `search`. Use `ids` for exact formal-card or relationship scope; optional `query` filters any collection. Search the full safe library when identity or knowledge matching requires it. `page_size` must be 1..48, never 50. Follow every short opaque `next_cursor` until `complete=true` by copying it exactly and keeping all other query arguments unchanged; never edit or synthesize a cursor. Do not cite an object that was not returned in this stage.

The following narrow Host transport rule applies only to math `search_records` in both Analysis and fresh Critical Review, and overrides the shared contract's general fail-closed sentence for `OUTPUT_LIMIT`. Use only the page-size ladder `48`, `24`, `12`, `6`, `3`, `1` for `search_records`. Within one successful page-size attempt, copy each `next_cursor` exactly and keep the page size fixed until the cursor chain reaches `complete=true`. If any page returns `OUTPUT_LIMIT`, abandon the entire unfinished attempt at that page size: none of its previously successful pages is evidence and none may contribute to the canonical transcript, duplicate ledger, coverage, grounding, or package. Immediately retry the same logical query at exactly the next smaller ladder value with no cursor, restarting from the first page; never carry an old cursor across a page-size change. Only a fully closed restarted chain is successful. If page size `1` returns `OUTPUT_LIMIT`, the logical query is exhausted, may be reported as `limited_by_evidence`, contributes no evidence, and must not be retried. Do not interleave another tool or query while a lower-tier restart is required.

Critical Review runs in a fresh model context bound to the immutable Analysis draft hash. It must independently call `get_task_context`, reread every task artifact to completion, and call at least one library tool that supports or refutes a key draft judgment. It cannot approve from the draft alone. Analysis and Critical Review bind the same generation and authority but have distinct MCP transcripts. In every stage, copy exact `mcp-item:math:<sha256>` refs only from rows that stage actually consumed. A tool call without stage-local grounding is invalid, and a ref returned only to the other stage proves nothing for the current stage.

Immediately before returning either stage, build a stage-local evidence-ref ledger from the exact `evidence_ref` strings in that stage's completed canonical MCP tool results. Recursively enumerate every string in the final structured output that matches `mcp-item:math:<sha256>` and compare all 64 hexadecimal characters byte for byte against that ledger. A one-character substitution, omission, insertion, case change, prefix change, or ref copied only from an abandoned `OUTPUT_LIMIT` attempt is fatal. Never guess, repair, shorten, normalize, or fuzzy-match a ref. If a cited ref is not an exact ledger member, remove every claim that depends on it or perform a new valid MCP read and copy the newly returned ref exactly; then repeat the complete membership audit. Critical Review may additionally cite an exact Analysis ref only through the Host-provided prior-ref contract, never by reconstructing it from memory.

## Semantic decisions

Classify the question as existing, new candidate, or `identity_ambiguous`. Similarity alone never proves identity. For each atomic knowledge, method, error, trap, or question-type signal, use only the proposal operations defined by `luna_proposal_v2`: `mark_existing_item`, `propose_item_update`, `propose_new_item`, `mark_existing_knowledge`, `propose_new_knowledge`, `propose_relation`, or `needs_review`. A new target always uses a temporary identifier. These names describe candidate actions for later Sol review; none performs a formal mutation.

Use `propose_item_update` for an existing card and `propose_new_item` for a new question. Propose a relation only from concrete shared structure, the same first action, the same specific trap, or a verified prerequisite/progression relationship. Broad chapter overlap, generic method names, or text similarity is insufficient.

For an independently correct episode, preserve the user's explicit independent-correct report as an observation. If no contradictory evidence exists, the absence of a step-by-step transcript cannot justify `propose_new_item`, a wrong-item update, a weakness claim, or invented reasoning. Keep every unobserved step `unknown`; return only an evidence-bounded learning observation or `needs_review` when the report conflicts with evidence. Do not infer mastery beyond the observed episode.

For a wrong-then-corrected episode, identify the first break before later distinct breaks, keep independently correct steps separate, and label explanation-dependent correction and later transfer evidence separately. Produce only proposal-only weakness distillation for Sol review. Do not convert post-explanation correctness into independent mastery, do not create a duplicate wrong item for an existing identity, and do not claim that any weakness, card, knowledge node, status, or relation was formally changed.

For source route `new_source_learning_episode`, keep the formal identity absent and preserve the stable source locator until Sol independently resolves identity. Do not invent or inherit a formal identifier from a nearby or similar record. Preserve every evidenced first break, later break, independently correct step, and explanation-dependent resolution as separate claims. A new wrong-item candidate, new or existing knowledge markers, weakness candidates, and relation candidates are permitted only as proposal-only operations for Sol review. Every new target uses a temporary candidate or capture identifier; no formal identifier is allocated and no formal mutation is claimed.

For a relation decision, copy the actual MCP relationship item's `stable_id` as `candidate_id` and use `mcp_relationship.<stable_id>` as its relationship reference. Emit at most five relation proposals selected by the reviewer from evidence it actually read. The host does not rank these proposals.

## Review and mathematical integrity

The reviewer checks mathematical correctness, object roles, conditions, image/text consistency, first-break order, hint dependence, identity boundaries, relation support, and new-knowledge granularity. Exact correction paths and canonical deltas must materially change the validated draft; an unresolved blocking issue requires rejection.

The analysis output has one shared hard budget of at most 64 claim objects across every section, including first-break and first-error claims. Except for reasoning reconstruction, every claim-list field accepts at most one precise claim; reasoning reconstruction accepts at most 6 claims, and the whole output accepts at most 16 atomic signals. State each fact or inference once in its narrowest owning section; do not duplicate the same claim across evidence, diagnosis, knowledge, method, formalization, risk, or Sol-check sections. Optional sections that add no distinct decision must be empty lists. Depth means precise evidence binding, not filling every list.

If `evidence_assessment.completeness` is `complete`, provide non-empty evidence inventory, reasoning reconstruction, `must_verify`, and `identity_checks`. If it is `limited_by_evidence`, provide non-empty `gaps`, top-level `unresolved`, and `reject_if`; these three fields are mandatory fail-close gates for limited evidence. Never select a completeness value whose corresponding gate fields are empty.

Use valid inline delimiters `\(` and `\)` in ordinary output strings. Keep geometry objects, parameter ranges, functions, differentials, expressions, and results distinct. Preserve evidence boundaries and Sol verification actions.

At the parsed-string layer, a mathematical command must contain exactly one backslash, for example \sqrt, never two adjacent backslashes. At the JSON source-byte layer, encode that single parsed backslash exactly once: the valid JSON string is "\\(R=1+\\sqrt{1-y^2}\\)"; the source form "\\(R=1+\\\\sqrt{1-y^2}\\)" is invalid because it parses to a doubled command escape. Apply the same rule to every LaTeX command and check the complete structured output before returning it.

Immediately before returning either Analysis or fresh Critical Review, recursively inspect every string leaf in the complete structured output, including strings nested in objects or arrays and values decoded from `canonical_json` correction wrappers. This scan covers claim text, evidence boundaries, Sol verification actions, and review findings. Every token consisting of a backslash followed by ASCII letters should be inside one balanced `\( ... \)` inline-math span. Do not check only fields that visually look like formulas. If prose needs only an ellipsis, write the Unicode character `…`; do not emit a bare `\ldots` command. Do not wrap an otherwise unintended command merely to satisfy this check, and do not add extra backslashes; correct the intended text before returning. A legitimate mathematical command may remain when it is part of the intended expression and is inside valid delimiters. After applying any Critical Review correction, repeat the complete recursive scan.

The Host applies `math-format-severity-v1` after preserving the raw Provider payload. Whitelisted presentation-only differences, such as an unambiguous bare ellipsis command, may be normalized only on a separately content-addressed validation copy and recorded as `completed_with_format_warnings`; they do not terminate Analysis. A known mathematical expression whose missing delimiter could hide a content error is preserved as `completed_needs_review` and must be examined by the fresh Critical Review. Unknown or dangerous commands, malformed JSON, unreadable role structure, false evidence, authority drift, cross-subject content, and formal-write claims remain fail-closed. Format normalization never changes MCP transcripts, evidence membership, mathematical meaning, proposal actions, or the raw Provider payload.

## Output boundary

Return proposal-only data compatible with `luna_proposal_v2`. The Host binds the untouched raw Provider payload and the separately normalized validation result to the capture-freeze receipt, both MCP transcripts, both grounding manifests, format-normalization receipts, and the final HMAC read-session receipt; it must not reinterpret mathematical semantics. Temporary candidate identifiers are allowed; formal identifiers are not. Do not modify repositories, allocate formal IDs, rebuild indexes, update mastery, call Sol, or claim a completed write. `formal_write_count=0`.
